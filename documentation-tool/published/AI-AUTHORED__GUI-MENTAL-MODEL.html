What stays shared when the GUI backend changes?

Application sends Snapshot data outward and receives Event input inward through a common Adapter contract. Feature decisions and Store calls remain shared. The host selects the concrete backend that implements the contract.

  • Application/handle show one application; Adapter/FLTK show one adapter through its interface and implementation.
  • Shared controls and handlers stay in Application; supported capabilities are still part of the backend contract.

When does creating a widget become something visible?

Application::add fills the owned view model. Application::publish stages the next Snapshot, computes shared layout and asks the adapter to present it. The concrete backend performs toolkit painting.

  • The constructor and event handlers decide when to call publish.
  • publish assigns the staged Snapshot to view_ after present returns successfully.

Which shared functions run when the Add button is clicked?

The backend reports an activation for entries.add. The shared handler routes it to append_entry, which calls Store::add. Control returns through the helper to the handler, and the handler publishes the resulting state.

  • Expected input/capacity rejection is caught by the helper and published as shared status.
