event and flow only after the arithmetic is understood. Infrastructure becomes
the surrounding support for that algorithm; do not scroll through large files.

MAIN APPLICATION: WHICH FILES TO EDIT

- src/store.cpp + include/foundation/store.hpp
  The Entry-list application's data behavior and public declarations. Store::add
  is src/store.cpp:33–45; Store::update is :47–55. The public Record/Store types are
  include/foundation/store.hpp:14–43. Change an existing function's implementation
  in store.cpp. Change the header when the callable interface, public data types
  or public contract changes. Add corresponding cases to tests/store_test.cpp.
- rust/text_validation/src/lib.rs
  The default Rust algorithm. validate_text at :11–19 accepts 1..256 printable
  ASCII bytes; the private C ABI wrapper is :27–39. Native callers pass through
  src/text_validation.h and src/text_validation.cpp. Algorithm-only changes inside
  validate_text do not require a new GUI adapter. ABI changes require matched C
  declarations/layouts and callers. Tests in this lib.rs begin at :58.
- gui/shared/view_definition.hpp
  Shared handwritten GUI layout: widget IDs, kinds, labels, heights, ordering.
  The small view_definition array is :18–31. This is where the main application's
  widgets are declared. Forms mode does not import this handwritten C++ layout.
- gui/shared/application.cpp + gui/shared/application.hpp
  Shared GUI state and event meaning. Application::handle and append_entry own
  actions; application.hpp declares the Application class and state. This is the
  application-side code that calls Store and updates shared widget state.
- src/main.cpp
  CLI argument handling and composition. Edit it when changing the CLI interface.
- CMakeLists.txt:58
  foundation_core lists ordinary implementation files. Add a new C++ algorithm
  source with target_sources(foundation_core PRIVATE src/extra.cpp). Put its public
  declarations in include/foundation/extra.hpp or private declarations beside
  the implementation as appropriate; include that header in callers. Headers
  declare functions/types and are not separate compiled translation units.
- gui/CMakeLists.txt:28
  foundation_gui_application owns shared GUI implementation. Add shared UI source
  with target_sources(foundation_gui_application PRIVATE shared/extra.cpp).

The main root project enables only CXX (CMakeLists.txt:2). A new true C source
target also needs enable_language(C) or LANGUAGES C CXX in the adopting project.
The Simple C example already supplies this and is the clearer beginner route.

MAIN APPLICATION: WHAT SUPPORTS THE EDIT

- gui/hosts/ and gui/host/: native/browser composition and host services.
- gui/patches/: adaptations to retained generic GUI suppliers.
- visual/ui/: optional shared form/event runtime.
- visual/flow/: optional shared continuous processing runtime.
- third_party/: pinned supplier inventory, source and notices; third_party/sdk/

- cmake/: target/build policy; tools/: build/release/evidence helpers.
- .github/workflows/: CI, SDK preparation, application builds, certification,
  release promotion and package production.
- build/: generated build output; select separate build trees for differing targets.

These support files are available when needed. A gain formula edit belongs to
the algorithm source; a widget label edit belongs to the layout; a new source
file belongs to the chosen CMake target. Present those jobs positively and stop
once the viewer can locate the relevant owner.

COMPLETE ADD-A-C-FILE WORKFLOW

Example: extract or add a reusable offset helper in the copied Simple C project.
1. Create offset.h with a guard, C++ extern "C" guard and:
       float simple_c_offset(float sample, float offset);
2. Create offset.c:
       #include "offset.h"
       float simple_c_offset(float sample, float offset) {
           return sample + offset;
       }
3. In signal.c include "offset.h" and call:
       return simple_c_offset(sample * gain, 1.0f);
4. After add_library(simple-c-behavior STATIC signal.c events.c), add:
       target_sources(simple-c-behavior PRIVATE offset.c)
   The existing target is C17, and project LANGUAGES C CXX is already enabled.
5. Rebuild the copied project's configured tree; CMake regenerates membership
   and compiles offset.c as a separate C translation unit before linking it.
6. Run the independent expected-value checks above. The result remains 3,5,7,9
   at gain 2 and 1.5,2,2.5,3 at gain 0.5.
7. For a changed public signature also update its declaration and caller. If the
   helper is called inside an existing block, no new visual block is necessary.
   A new independent block needs a factory/adapter and design composition too.

RUST DSP: WHICH FILES, INTERFACE AND RESULTS

All paths share editor/examples/rust-dsp/.
- dsp.rs:23–47 owns process_samples, a three-tap FIR with coefficients
  [0.25,0.5,0.25], followed by decimation by two. Its key formula is :32.
- dsp.rs:55–85 owns the exported C ABI function foundation_rust_dsp_process.
- dsp.h:10–32 matches shared structs and declares that ABI to C/C++ callers.
- flow_adapter.cpp/.hpp wraps input/output buffers and persistent stream state.
- project.json owns Source -> Rust FIR/decimate 2 -> Collector composition.
- main.cpp owns independent algorithm/ABI/flow expectations.
- CMakeLists.txt:29–34 compiles the Rust static archive from existing rustc;
  :44–51 defines/links the ordinary C++ executable to the imported Rust archive.

Known reference vectors in main.cpp:
Input 1,2,3,4,5,6,7,8,9 -> output 1,3,5,7 (9 inputs consumed, 4 outputs produced).
Input 1,0,0,0,2,2,2,-1,4 -> output 0.5,0,1.5,1.25.
Each stream keeps its previous two samples and phase across chunk boundaries.
Output capacity can stop consumption before an output-due sample, preserving
history; restarting the graph creates fresh state. Do not describe this as gain.

DIRECT GITHUB LATEST / OS PACKAGE-MANAGER CONNECTION

Suggested viewer wording:
"Software Foundation brings GitHub Latest releases and distribution package
managers together. CI builds the application and formats its signed release
assets as package repositories. APT and pacman connect directly to the project's
Latest release URL, so the user's operating system fetches packages and normal
updates from CI-built releases. The project does not need a separately hosted
package repository. Gentoo follows Latest through the included verified sync
adapter, which pins the exact release tag before activating its overlay."

Precise checked-in evidence:
- docs/distribution-release.md:5–10: package repositories are ordinary release
  assets, built/signed before the candidate inventory freezes; no separate mirror.
- :12–23: signed metadata, combined APT index (amd64/arm64), flat Arch database
  (x86_64), signed native bundles and retained Gentoo inputs.
- :33–47: APT/pacman root is
      https://github.com/OWNER/REPOSITORY/releases/latest/download/
  APT uses a trusted key and flat suite ./; pacman uses Required DatabaseRequired
  and the same URL as Server. apt-get update / pacman -Syu discover promotion.
  Gentoo's trusted distro_client.py track=latest pins/verifies a tag and uses the
  Portage sync adapter; it is not a direct pacman-style HTTP database configuration.
- tools/release_packages.py:31–33 defines Latest/exact-tag base URLs.
- :321–335 generates actual INSTALL.md APT/pacman/Portage configuration.
- :381–404 creates native packages and APT repo using the Latest base URL.
- .github/workflows/_release-latest.yml:116–129 calls sdk-application.yml with
  require_regression: true and package_repository: true.
- docs/distribution-release.md:77–80 records the completed all-GUI/Rust release
